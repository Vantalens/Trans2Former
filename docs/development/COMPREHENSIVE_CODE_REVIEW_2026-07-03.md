## 详细发现

### P2 级问题（重要问题，计划修复）

#### 1. 启动时重复 DOM 查询（69次）
**文件**: `public/app.js:38-102`  
**问题**: 启动时使用 `getElementById`/`querySelector` 查询 69 个 DOM 元素并存储在全局变量中，阻塞启动路径  
**影响**: 启动路径增加 ~5-10ms，所有元素即使未使用也会被缓存  
**建议**: 对非关键路径元素使用懒加载 getter，按功能模块分组按需初始化  
**优先级**: P2 - 性能优化

#### 2. `hashString` 函数每次调用重新计算
**文件**: `public/app.js:349-356, 387-395`  
**问题**: `getHistoryStorageKey()` 每次被调用时都重新计算哈希，包括完整的文档内容  
**影响**: 对 50KB+ 文档，每次哈希计算耗时 10-50ms，影响读写 localStorage 性能  
**建议**: 实现 `cachedHistoryKey` 缓存（代码中已声明变量但未使用）  
**优先级**: P2 - 性能优化

#### 3. 格式解析器中大量 `matchAll` 嵌套循环
**文件**: `public/formats/pdf.js`, `docx.js`, `xlsx.js`  
**问题**: 多层嵌套的 `for...of...matchAll()` 循环，外层匹配大块，内层再逐个匹配小项  
**影响**: 
- PDF ToUnicode CMap 解析可能有 1000+ bfchar 条目
- XLSX 1000 行 × 20 列 = 20000 次 `matchAll` 调用
**建议**: 缓存外层 matchAll 结果数组，使用非捕获组减少内存分配  
**优先级**: P2 - 性能优化

#### 4. DOCX `scanBalanced` 深度计数器低效
**文件**: `public/formats/docx.js:69-88, 93-122`  
**问题**: 对每个标签都执行正则匹配和字符串切片，复杂 DOCX 可能触发 O(n²) 行为  
**影响**: 200 页 DOCX 全文扫描开销显著  
**建议**: 使用索引数组而非字符串切片，或考虑流式 XML 解析器（如 SAX）  
**优先级**: P2 - 性能优化

#### 5. ZIP deflate 解压中未优化的输出数组操作
**文件**: `public/core/zip-container.js:119-131, 133-150`  
**问题**: `copyDistance` 函数使用 `output.push()` 逐字节追加，每次 push 都可能触发数组重新分配  
**影响**: 
- 10MB 压缩文件可能执行数百万次 push 操作
- 数组动态扩容导致多次大块内存拷贝
**建议**: 预分配固定大小的 Uint8Array，使用索引写入而非 push  
**优先级**: P2 - 内存和性能

#### 6. `renderFileQueue` 每次调用都重新渲染整个队列
**文件**: `public/app.js:227-249`  
**问题**: 每次状态更新都重建整个队列 DOM，10+ 文件队列时频繁重绘导致 UI 卡顿  
**影响**: 批量处理时频繁全量 DOM 操作  
**建议**: 实现增量更新（仅更新变化的队列项），或对大队列使用虚拟滚动  
**优先级**: P2 - UI 性能

#### 7. `ensureDocumentAudit` 在转换管线中被重复调用
**文件**: `public/core/format-registry.js:369-373, 386-390, 463-470, 503-513, 555-566, 618-621`  
**问题**: 对同一个 model 可能调用 5+ 次，每次都遍历 model.blocks 和 metadata  
**影响**: 复杂转换路径（如 PDF → OCR → SemanticDoc → DOCX）开销累积  
**建议**: 仅在管线关键节点调用，中间 mapper 步骤跳过或使用轻量级验证  
**优先级**: P2 - 性能优化

#### 8. 转换完成状态可能无法正确更新 UI
**文件**: `public/app.js:1054`  
**问题**: 新逻辑在 "complete" 状态时跳过 `updateConversionProgress`，可能导致转换完成后 UI 无法正确显示最终状态  
**影响**: 
- 进度条可能卡在 99% 而不显示 100%
- 成功消息/图标可能未显示
- 下载按钮可能未启用
**建议**: 需要检查 `updateConversionProgress` 函数对 "complete" 状态的特殊处理逻辑  
**优先级**: P2 - 功能正确性

### P3 级问题（优化建议，择机修复）

#### 9. 重复的输出状态赋值
**文件**: `public/app.js:1565-1601`  
**问题**: `transformContent()` 中对 `currentOutputType/Format/Mime` 进行了重复赋值  
**建议**: 只在开头赋值一次，后续分支只处理差异化逻辑  
**优先级**: P3 - 代码清理

#### 10. 可推导的嵌套条件判断
**文件**: `public/app.js:570-652`  
**问题**: `renderVerificationReport()` 有 5 层嵌套的条件检查，包含大量可推导的局部变量  
**建议**: 提取独立的辅助函数，扁平化逻辑  
**优先级**: P3 - 可维护性

#### 11. 历史存储键的冗余计算
**文件**: `public/app.js:387-394, 402, 424`  
**问题**: `getHistoryStorageKey()` 在每次调用时都重新计算哈希，但依赖项在同一会话中很少变化  
**建议**: 在输入变化时调用一次 `updateCachedHistoryKey()`，read/write 直接使用 cachedHistoryKey  
**优先级**: P3 - 微优化

#### 12. 平衡标签扫描器重复
**文件**: `public/formats/docx.js:69-88, 93-122`  
**问题**: `scanBalanced()` 和 `scanTopLevelBlocks()` 包含几乎相同的深度计数逻辑  
**建议**: 统一为单个可配置的扫描器  
**优先级**: P3 - 代码复用

#### 13. 过深的提取函数嵌套
**文件**: `public/formats/pdf.js:192-242`  
**问题**: `extractLiteralTextOperators()` 包含 4 层嵌套  
**建议**: 拆分为独立的提取器  
**优先级**: P3 - 可读性

#### 14. 实体解码的链式 replace
**文件**: `public/formats/html.js:57-72`  
**问题**: `decodeHtmlEntities()` 使用 3 个链式 `replace()` 调用，每次都遍历整个字符串  
**建议**: 单次扫描处理所有实体  
**优先级**: P3 - 性能优化（大 HTML 文档）

#### 15. 队列项查找的重复模式
**文件**: `public/app.js:214-225, 251-257, 292-314`  
**问题**: `getActiveQueueItem()`, `updateActiveQueueItem()`, `processQueuedFiles()` 中重复使用 `fileQueue.find()`  
**建议**: 使用 Map 存储队列项，查找从 O(n) 降至 O(1)  
**优先级**: P3 - 性能优化（多文件场景）
