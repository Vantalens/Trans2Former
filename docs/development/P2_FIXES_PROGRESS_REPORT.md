### ✅ P2 #2: hashString 缓存优化

**提交**: `23b0a73`, `96da6eb`  
**文件**: `public/app.js:387-402, 1310, 1671, 1683, 1736, 1746`

**问题**:
- `getHistoryStorageKey()` 每次调用都重新计算完整文档哈希
- 对 50KB+ 文档，每次哈希计算耗时 10-50ms
- `writePersistentHistory()` 频繁调用导致性能瓶颈

**修复**:
1. 实现 `updateCachedHistoryKey()` 函数
2. 使用 `cachedHistoryKey` 缓存计算结果
3. 在输入内容、格式、配置变化时使缓存失效

**失效时机**:
- 文件名变化（`handleInputText`）
- 输入内容变化（`inputContent` input 事件）
- 输入格式变化（`fromFormatSelect` change）
- 输出格式变化（`toFormatSelect` change）
- Markdown 配置变化（`markdownProfileSelect` change）

**影响**:
- 减少重复哈希计算
- 提升大文档的 localStorage 读写性能
- 避免每次版本提交都重新计算哈希

**验证**:
- ✅ 所有测试通过（43/43）
- ✅ 缓存在正确时机失效
- ✅ `getHistoryStorageKey()` 使用缓存

## 经验教训

### 成功经验

1. **缓存优化模式**: 
   - 声明缓存变量
   - 提供更新函数
   - 在正确时机失效
   - 懒加载初始化

2. **小步修复原则**:
   - 单个问题单独提交
   - 充分测试验证
   - 清晰的提交信息

### 遇到的挑战

1. **ZIP 解压优化的复杂性**:
   - 性能优化可能改变错误检测行为
   - 需要保持与现有测试的兼容性
   - LZ77 算法的正确实现需要深入理解

2. **测试期望的严格性**:
   - 错误代码和错误时机都有明确期望
   - 性能优化不能牺牲正确性

### 改进建议

1. **性能基准测试**: 建立性能基准，量化优化效果
2. **渐进式优化**: 从简单、低风险的优化开始
3. **错误兼容性**: 性能优化时保持错误检测行为一致
